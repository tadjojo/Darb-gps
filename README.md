# DARB GPS API — NestJS alpha foundation

This is a **starter foundation**, not a production-ready tracking service.

## Included
- NestJS 11 modular application structure.
- Environment validation (Joi); no development token or embedded secret.
- PostgreSQL pool with graceful shutdown.
- Liveness/readiness endpoints (readiness checks PostgreSQL and Redis when configured).
- Strict request validation and an initial mobile-location DTO.
- Initial PostGIS schema and transactional outbox with lease-based publisher to Redis Streams (requires `REDIS_URL`; optional in local development).
- Login with bcrypt password verification, short-lived JWT access tokens, hashed opaque refresh tokens and single-use refresh rotation.
- JWT-protected mobile device enrollment/revocation and location ingestion; vehicle membership authorization; duplicate-event protection; transactional location + latest-location + outbox writes.

## Not yet implemented
- MFA, password-reset and account-verification flows.
- Rate limiting, audit pipeline, retention/partitioning, monitoring, backups.
- Flutter background tracking, offline queue integration and release builds.

The login endpoint assumes users are provisioned with a bcrypt password hash; there is no public registration endpoint. Organization and vehicle membership APIs are available in this alpha, but initial user provisioning remains controlled. Add rate limiting and MFA before production. Do not expose this alpha as a production API.

## Local setup
1. Install Node.js 20+ and Docker Compose. Copy `.env.example` to `.env`, set a long random `POSTGRES_PASSWORD` and a distinct strong `JWT_ACCESS_SECRET`.
2. Start local infrastructure: `docker compose up -d postgres redis`.
3. Set `DATABASE_URL=postgresql://darb_app:<password>@localhost:5432/darb_gps` and `REDIS_URL=redis://localhost:6379` in `.env`.
4. Install dependencies: `npm install`.
5. Apply migrations with `npm run migration:up` (ensure `DATABASE_URL` is available to node-pg-migrate).
6. Run `npm run start:dev`. The API listens on port 3000 by default.

Health endpoints (with default prefix):
- `GET /api/v1/health/live`
- `GET /api/v1/health/ready`

A `Dockerfile` is included for building the API image; `docker-compose.yml` starts only the local PostGIS and Redis infrastructure. Before production, configure TLS to the database, secret management, explicit CORS
origins, backups/PITR, observability, rate limits, security review and tested migrations.


## Tracking alpha endpoints

- `POST /api/v1/tracking/devices/enroll-mobile` — JWT required; body `{ "vehicleId": "<uuid>" }`. Creates a mobile device record; mobile location requests use the authenticated user JWT and the device-to-user/vehicle binding.
- `POST /api/v1/tracking/mobile/location` — JWT required; accepts eventId, deviceId, vehicleId, latitude, longitude, accuracyMeters, recordedAt and optional speedKmh/heading.
- `GET /api/v1/tracking/vehicles/:vehicleId/latest` — JWT required; requires active vehicle membership.
- `POST /api/v1/tracking/devices/:deviceId/revoke` — JWT required; vehicle owner/manager only.

Vehicle membership is represented by `vehicle_members`; organization creators become vehicle owners, while fleet supervisors become vehicle managers on vehicles they create. The location pipeline is transactional and idempotent by `(device_id,event_id)`. It rejects timestamps older than seven days or more than five minutes in the future and rejects reported accuracy worse than 250m. These are initial policy thresholds and should be tuned from pilot data.

The outbox publisher claims rows with `FOR UPDATE SKIP LOCKED`, leases them to one worker, and writes to Redis Streams before marking them published. A consumer group forwards vehicle-location events to authenticated Socket.IO rooms. Clients must reconnect and fetch the REST latest-location endpoint because a socket emission is not a durable per-client delivery guarantee. Stream delivery is at-least-once; clients should deduplicate by `outboxId` or `eventId`. Configure Redis persistence/replication and monitor stream growth; no automatic trimming is applied because it could discard unconsumed events. Independent tracker HTTPS ingestion is now available for the documented NMEA RMC, GT06 0x12 and normalized JSON formats; other vendor variants and raw TCP/UDP/MQTT listeners remain unsupported. Do not expose this build as a production service before security review, migration testing, automated tests, load tests, and TLS/deployment hardening.

### First owner provisioning

There is intentionally no public signup endpoint in this alpha. Use the controlled SQL template in `docs/bootstrap-first-vehicle.sql` to provision the first account, organization, vehicle and owner membership. Supply a bcrypt hash generated by a trusted password-hashing tool; do not store a plaintext password in SQL, shell history or source control.


## Organization and fleet endpoints (alpha)

All endpoints below require `Authorization: Bearer <access-token>`:

- `POST /api/v1/organizations` — body `{ "name": "Company name" }`; creates an organization and makes the caller its `org_admin`.
- `POST /api/v1/organizations/:organizationId/vehicles` — body `{ "displayName": "Truck 01", "registrationNumber": "..." }`; organization admin/fleet supervisor only. Creator is added as vehicle owner.
- `GET /api/v1/organizations/:organizationId/vehicles` — lists vehicles for active organization members.
- `POST /api/v1/vehicles/:vehicleId/members` — body `{ "userId": "<uuid>", "role": "manager|driver|viewer" }`; vehicle owner/manager may add an active member of the same organization.

## Realtime location channel (alpha)

Connect with Socket.IO to `/tracking` using the access token in `auth: { token }`. Then emit `vehicle.join` with `{ "vehicleId": "<uuid>" }`. The server checks active vehicle membership before joining `vehicle:<uuid>`. Location messages arrive as `vehicle.location.updated`. On reconnect, call `GET /api/v1/tracking/vehicles/:vehicleId/latest` to reconcile state. Configure `CORS_ORIGINS` as a comma-separated allowlist for browser clients.

The Redis consumer uses a dedicated Redis connection and a consumer group. It acknowledges an event after the server-side room emit; this does not prove any particular client received it. A crash between emit and acknowledgement can cause a duplicate, so client deduplication is mandatory. Membership changes and logout now trigger per-instance revocation fanout, and connected sockets are revalidated periodically. The revocation listener and two-instance behavior still require runtime integration tests before production.

See `docs/implementation-status.md` for implemented scope, delivery semantics, validation performed and production blockers.


### Logout and access-token revocation (alpha update)

`POST /api/v1/auth/logout` accepts the refresh token in its JSON body and, when available, the current access token in the `Authorization: Bearer` header. The server revokes both the refresh session and the access token JTI until its expiry. HTTP guarded routes and newly established Socket.IO connections reject that JTI. This does not yet force-close a socket that was connected before logout; that requires a distributed disconnect/revocation event and is a production blocker.

## Independent GPS tracker gateway (phase 5464)

- `POST /api/v1/tracking/devices/enroll-gps-tracker` — JWT required; vehicle owner/manager only; body `{ "vehicleId": "<uuid>", "label": "Truck GPS 01" }`. The raw 256-bit bearer credential is returned once; only its SHA-256 hash is stored.
- `POST /api/v1/device-gateway/ingest` — device bearer credential required; body `{ "protocol": "nmea0183|gt06|json", "payload": "..." }`.
- NMEA 0183 RMC, GT06 location packet `0x12` (including the documented CRC-ITU and course/status hemisphere bits), and normalized JSON adapters are included. All feed the same idempotent transactional location/latest/outbox pipeline. HTTPS only; raw TCP/UDP/MQTT listeners and other vendor-specific packet variants are not included yet.
- Apply `002_tracker_protocols.js` with `npm run migration:up` before using tracker provisioning/ingestion.

## Automated tests and two-instance profile (phases 5462–5463)

- `npm run test:unit` runs protocol adapter unit tests.
- `DATABASE_URL=... REDIS_URL=... npm run test:integration` runs PostGIS schema and Redis multi-consumer-group integration checks. Tests are skipped when their service URL is absent.
- `./scripts/deploy-multi-instance.sh` validates required secrets, starts PostGIS/Redis, runs migrations in a dedicated build-stage migration container (which includes `node-pg-migrate`), and then starts two API replicas and Nginx on port 8080. The migration container is intentionally separate because the runtime API image omits development dependencies.
- This profile demonstrates two API processes, not production HA: the sample PostgreSQL and Redis services are single instances.

### Independent GPS device operations (phase 23)

The tracker simulator supports repeated reports and exact duplicate replays. Example (after provisioning a tracker credential):

```bash
node scripts/simulate-tracker.mjs --url http://localhost:3000/api/v1/device-gateway/ingest --credential '<token>' --protocol json --repeat 12 --interval-ms 5000 --duplicate true
```

Owners/managers provision devices with `POST /api/v1/tracking/devices/enroll-gps-tracker`; the bearer token is returned once. Device state and supported telemetry are available from `GET /api/v1/tracking/devices/vehicle/:vehicleId`. Revoke lost devices with `POST /api/v1/tracking/devices/:deviceId/revoke`. See `docs/phase-23-independent-device-operations.md` for transport limitations and the operational checklist.

### Repeatable multi-instance deployment (phase 24)

Copy `.env.example` to `.env`, set `POSTGRES_PASSWORD` to at least 24 non-placeholder characters and `JWT_ACCESS_SECRET` to at least 32 non-placeholder characters, then run `./scripts/deploy-multi-instance.sh`. The script applies migrations before starting the API replicas. The sample deployment binds the load balancer to `127.0.0.1:8080`; place a TLS reverse proxy in front of it before any public exposure.
