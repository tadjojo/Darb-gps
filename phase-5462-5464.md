# DARB GPS — phases 5462–5464

## 5462 — automated integration coverage

- Jest configuration added with separate unit and integration commands.
- Protocol unit tests cover valid NMEA RMC checksum/coordinate/time parsing, invalid checksum/fix, GT06 framing/CRC/location extraction, and normalized JSON validation.
- PostgreSQL integration check verifies PostGIS and the tracker metadata migration.
- Redis integration check creates two independent consumer groups and proves both replica groups can read the same stream event.
- Integration tests are opt-in: they run only when `DATABASE_URL` / `REDIS_URL` are provided. No claim of passing runtime integration tests without those services.

## 5463 — two-instance deployment profile

Run from `backend/` after configuring `.env` with a strong `POSTGRES_PASSWORD`, `JWT_ACCESS_SECRET` (at least 32 characters), and production CORS origins:

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.multi-instance.yml up --build -d
```

Apply migrations once:

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.multi-instance.yml run --rm api-1 npm run migration:up
```

The profile starts two API instances with distinct stable `INSTANCE_ID` values, shared PostGIS/Redis, and an Nginx reverse proxy on `127.0.0.1:8080`. Socket.IO uses WebSocket transport and the proxy forwards upgrades. This is a local deployment profile, not a high-availability production topology: PostgreSQL and Redis are still single instances and require managed HA/replication, backups, TLS, secrets, and monitoring before production.

Test commands:

```bash
cd backend
npm install
npm run test:unit
DATABASE_URL=... REDIS_URL=... npm run test:integration
```

## 5464 — independent GPS tracker gateway

### Provisioning

`POST /api/v1/tracking/devices/enroll-gps-tracker` (JWT; owner/manager only):

```json
{ "vehicleId": "<vehicle-uuid>", "label": "Truck GPS 01" }
```

The API returns a random 256-bit bearer credential once. Store it in the tracker securely; the server stores only its SHA-256 hash. A lost credential must be revoked and replaced, not retrieved.

### Ingestion

`POST /api/v1/device-gateway/ingest`

Headers: `Authorization: Bearer <device-credential>`

Body examples:

```json
{ "protocol": "nmea0183", "payload": "$GPRMC,...*HH" }
{ "protocol": "gt06", "payload": "7878...0d0a" }
{ "protocol": "json", "payload": "{\"latitude\":31.95,\"longitude\":35.91,\"recordedAt\":\"2026-11-05T10:00:00Z\"}" }
```

Adapters normalize into latitude, longitude, speed, heading, accuracy estimate and recorded timestamp. The gateway validates timestamp bounds, deduplicates by a stable UUID derived from protocol + raw payload, persists location/latest pointer/outbox transactionally, and updates device last-seen/protocol.

### Protocol limits

- NMEA 0183: RMC sentence only; checksum required; speed converted from knots to km/h. GGA-only feeds are not accepted yet.
- GT06: location packet protocol `0x12` only; validates framing, length and CRC-ITU checksum using the vendor manual algorithm; a published Concox sample frame is included in the unit tests. Other GT06 variants, login packets, alarms and vendor extensions are not yet supported. Verify bit/coordinate interpretation against each device vendor's manual and real packet captures before field use.
- JSON: normalized vendor-independent adapter for test rigs and devices with a configurable upstream translator.
- No raw TCP/UDP/MQTT listener, IMEI bootstrap, per-vendor protocol auto-detection, command channel, or device-side configuration management yet. Gateway currently accepts authenticated HTTPS payloads only.
- Accuracy for NMEA/GT06 is an adapter estimate, not a measured GNSS accuracy value unless the source protocol provides it.

The mobile Flutter project is retained unchanged in this increment; its existing mobile enrollment and GPS ingestion endpoints remain available.
