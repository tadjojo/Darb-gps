# DARB GPS – phases 5465–5467

## 5465 – Independent tracker simulator

`backend/scripts/simulate-tracker.mjs` uses Node.js 20+ built-in `fetch` to send protocol payloads to `/api/v1/device-gateway/ingest`. It can replay a packet to exercise server-side idempotency, retry after network errors, and intentionally suppress the first send to model a disconnected interval. JSON and NMEA RMC test payloads can be generated; GT06 requires a captured or known-valid hexadecimal location frame supplied with `--payload-file`.

Examples (run from `backend/`):

```bash
npm run simulate:tracker -- --url http://localhost:3000/api/v1/device-gateway/ingest --credential '<one-time-device-secret>' --protocol json --duplicate true
npm run simulate:tracker -- --url http://localhost:3000/api/v1/device-gateway/ingest --credential '<one-time-device-secret>' --protocol nmea0183 --simulate-drop-first true --retries 4
npm run simulate:tracker -- --url http://localhost:3000/api/v1/device-gateway/ingest --credential '<one-time-device-secret>' --protocol gt06 --payload-file ./fixtures/location-frame.hex
```

The simulator does not create a real RF/network outage, does not emulate a tracker modem, and does not implement the raw TCP GT06 login/acknowledgement exchange. It tests the existing HTTPS ingestion contract only. The server's deterministic event ID means an identical protocol+payload replay is treated as a duplicate; devices that produce different payload bytes for the same physical fix need a protocol-specific sequence/IMEI identity strategy in a future adapter.

## 5466 – Device registry

Migration `003_device_registry.js` adds a model catalogue and optional manufacturer/model, IMEI, serial, firmware, hardware and telemetry columns. IMEI uniqueness is enforced only for non-empty values. Endpoints:

- `GET /api/v1/tracking/devices/vehicle/:vehicleId` – authenticated vehicle member; returns enrolled devices and a simple connection-state estimate.
- `PATCH /api/v1/tracking/devices/:deviceId/metadata` – owner/manager; updates device identity and telemetry metadata.

The `online` label currently means a tracker heartbeat/location was received within 120 seconds; this is a provisional UI heuristic, not a protocol-level guarantee. Battery and RSSI are stored when explicitly reported through the metadata endpoint. Automatic telemetry ingestion is not yet enabled for the current GT06 0x12-only parser.

## 5467 – Protocol integration readiness

- JSON and NMEA RMC can be generated by the simulator.
- GT06 location frame can be submitted from a known-valid packet fixture.
- Replays use the existing database uniqueness constraint `(device_id,event_id)`.
- Existing Flutter source is intentionally unchanged.

## Validation boundary

The migration and script are syntax-checked in the development environment. PostgreSQL migrations, NestJS build, HTTP simulator against a live API, Redis/PostGIS integration and physical tracker tests require services/toolchains not present in this environment and remain pending. No claim of live device compatibility is made. The current gateway accepts an HTTPS wrapper carrying GT06 hex; it is not yet a raw TCP GT06 server.

## 5468 – JSON tracker telemetry

The normalized JSON adapter now accepts optional `batteryPercent` (0–100), `signalStrengthDbm` (-160–0), and `networkType` (up to 30 characters). Values are validated and updated in the same database transaction as the accepted tracker event. Missing telemetry never erases the last known value. The simulator's default JSON sample includes example telemetry values. NMEA RMC and the current GT06 location packet do not populate these fields; their support requires protocol-specific telemetry packets/adapters.
